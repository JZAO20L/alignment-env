# 文档体系规范（Meta）

> **状态**：`active`（本文档是仓库文档体系的唯一规范来源）
> **定位**：定义本仓库文档的分层、每类文档的职责边界、更新时机与命名约定。
> **适用**：所有版本。与版本级设计文档正交——那些回答"做什么、为什么"，本文档回答"文档放哪、写什么、什么时候更新"。

本文档沿用 evolving-harness 的文档规范（`~/evolving-harness/docs/README.md`），按本仓库规模做了收敛。

## 1. 角色模型

| 角色 | 职责 |
|---|---|
| **用户** | 定方向、拍板、验收、提供真实运行环境的观察 |
| **Agent** | 实现代码 + 维护全部文档 |

无 Worker / Reviewer 分工。**一次变更没有同步更新受影响的文档，视为未完成**——文档是变更的一部分，不是补写。REVIEW 的三件事（缺陷清单 / 修复优先级 / 泄准验收）分别落到 REPORT 的"问题与风险"、TODO 的优先项、交付前自检清单。

## 2. 文档分层

```
README.md                             L0  项目是什么 / 为什么 / 怎么开始（英文，公开）
docs/README.md                        L1  文档体系规范（本文件，中文）
docs/vX.Y/README.md                   L2  本版本：范围、状态、里程碑、索引
docs/vX.Y/DESIGN_vX.Y_<topic>.md      L3  为什么这么做、做成什么样
docs/vX.Y/TODO_vX.Y.md                L3  下一步做什么、做到什么算完成
docs/vX.Y/COOKBOOK_vX.Y_<topic>.md    L3  怎么跑、怎么排障
docs/vX.Y/REPORT_vX.Y_<milestone>.md  L3  做成了什么、证据是什么
<code dir>/README.md                  L4  目录是什么、文件怎么组织
```

版本目录内拍平：一个版本一个目录，不建 `design/ todo/ ...` 子目录；单版本目录不超过 6 个文件。

## 3. 文档类型

| 文档 | 必须包含 | 禁止包含 |
|---|---|---|
| 根 README | 一句话定位、快速开始、文档入口 | 版本流水账、内部实验细节 |
| 版本 README | 范围、状态、里程碑、索引 | 详细方案（进 DESIGN） |
| DESIGN | 目标与非目标、约束、方案与取舍、接口、验收 | 任务清单、执行命令 |
| TODO | 带编号任务、优先级、验收条件 | 长篇方案论证 |
| COOKBOOK | 可复制命令、预期输出、常见错误 | 设计论证、结果分析 |
| REPORT | 结论、证据（commit/trace/测试）、偏差、风险 | 泛泛的"已完成" |

## 4. 边界铁律

1. README 不复述设计理由（why 进 DESIGN）。
2. COOKBOOK 不含论证；REPORT 数字必须可追溯（commit / run_id / 测试输出），不可比的标"不可比"。
3. DESIGN 只写当前版本，不写"曾经考虑过"。
4. 时点产物不原地改：DESIGN/TODO/REPORT 关闭后冻结，修订开新版加 `superseded-by:`。
5. 目录 README 只写现状，不写"计划中的代码"。

## 5. 版本与生命周期

- 版本号只在能力边界变化时递增，不为重构/bugfix 开新版。
- 版本生命周期：`planning → active → frozen`；归档靠 git tag，不搬目录。
- 文档首行状态头：`> **状态**：active | frozen | superseded-by:<path>`。

## 6. 交付前自检

- [ ] 代码能跑（关键路径实测通过）
- [ ] 文档与代码一致（目录 README 描述的文件真实存在）
- [ ] 结论可追溯
- [ ] TODO 已对账
- [ ] 设计偏差已写进 REPORT
- [ ] 没把"计划"写进"现状"文档

## 7. 书写

- 根 README 用英文；`docs/` 用中文；代码标识符保持原文。
- 日期一律绝对日期 `YYYY-MM-DD`；相对路径链接；表格优先；结论先写。
